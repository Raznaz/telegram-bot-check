# Design

## Context

Сейчас источник данных один: `fetchOutages()` в `src/parser/voda-uz.ts` запрашивает 20 последних постов REST API WordPress, фильтрует их по заголовку и кэширует результат на 5 минут одной записью. Планировщик вызывает её с `force=true`, `/schedule` без него. В базе нет ни заголовков, ни дат, только `seen_outages(id, status)`.

Что проверено на живом API:
- `after` фильтрует по времени публикации, `per_page` не больше 100, число страниц приходит в `X-WP-TotalPages`.
- За 90 дней публикуется около 60 постов (всех типов), из них около 15 отключений.
- 247 постов за 2026 год весят 1,65 МБ вместе с телами. Большая часть веса приходится не на отключения.
- Дата `date` на сайте сдвинута относительно `date_gmt` на 3 часа, поэтому точные границы надо считать по `date_gmt`.

Мотивация и состав изменения: см. proposal.md, требования: см. specs/outage-history/spec.md.

## Goals / Non-Goals

**Goals:**
- Дать `/history` без новой таблицы, зависимостей и миграции.
- Сохранить возможность позже заменить источник на SQLite, не меняя команду.
- Не создавать лишней нагрузки на сайт при нажатии кнопок.

**Non-Goals:**
- Собственное хранилище истории (запасной вариант B).
- Выбор произвольных дат и период больше 90 дней.
- Кнопочная пагинация длинных результатов (длинный результат просто делится на несколько сообщений).
- Изменение поведения `/schedule` и планировщика.

## Decisions

### 1. Одна функция «отключения за период» как шов для варианта B

В парсере появляется `fetchOutagesSince(days)`, а команда `/history` знает только о ней. Сегодня она ходит в API, а если позже история перейдёт в SQLite, подменится реализация внутри функции.

Альтернатива: вызывать из команды запрос к API напрямую. Отброшено: замена источника потребовала бы переписывать команду.

### 2. Всегда грузить окно 90 дней, а периоды 7 и 30 вырезать на клиенте

Один запрос окна 90 дней, кэш на 5 минут, дальше 7 и 30 дней получаются фильтрацией по `publishedAt`. Нажатие других кнопок в течение пяти минут обходится без обращения к сайту, кэш один, а не по периодам.

Альтернатива: отдельный запрос и отдельная запись кэша на каждый период. Отброшено: больше запросов и кода без выигрыша, окно 90 дней и так укладывается в одну страницу.

### 3. Границы периода: запрос с запасом, точная обрезка по `date_gmt`

В запрос уходит `after = (сейчас − 90 дней − 1 день)`, а затем записи фильтруются по `publishedAt >= сейчас − N дней`, где `publishedAt` берётся из `date_gmt`. Так сдвиг часового пояса на стороне сайта не может ни отрезать нужную запись, ни пропустить лишнюю.

### 4. Постраничная загрузка с ограничением

`per_page=100`, страницы запрашиваются подряд, пока приходит полная страница, но не больше 5 страниц. Реальный объём (около 60 постов) укладывается в одну страницу. Ограничение защищает от бесконечного цикла при неожиданном поведении API. При достижении предела в лог пишется предупреждение, а пользователь получает то, что загружено.

### 5. Кэш хранит промис, а не данные

Запись кэша содержит промис текущего запроса и время его создания. Одновременные нажатия разных пользователей используют один запрос, а при ошибке запись удаляется, чтобы следующая попытка повторила запрос, а не вернула закэшированный сбой.

Альтернатива: хранить готовый результат, как в `fetchOutages`. Отброшено: два одновременных запроса к сайту при пуске, и ошибка могла бы кэшироваться.

### 6. Тела постов загружаются в том же запросе

Поиск по подпискам идёт по заголовку и телу (как в `/schedule`, через общую `matchesKeyword`), поэтому в запросе остаётся `content`. Оценка размера: сотни килобайт на запрос окна 90 дней, раз в пять минут.

Альтернатива: двухшаговая загрузка (сначала заголовки, потом тела только отключений через `include=`). Заметно легче по трафику, но два запроса и больше кода. Откладывается до момента, когда объём станет проблемой.

### 7. Разбор постов переиспользуется

Преобразование поста в `Outage` (очистка HTML, определение статуса, фильтр по заголовку) выносится из `fetchOutages` в общую функцию, которой пользуются оба запроса. Фильтр отключений остаётся прежним, так что история и `/schedule` согласованы в том, что считается отключением.

### 8. Кнопки и обработка нажатий

`/history` отвечает сообщением с `InlineKeyboard` из трёх кнопок с данными вида `history:7`, `history:30`, `history:90`. Нажатие обрабатывается `bot.callbackQuery`, и на него всегда отвечают `answerCallbackQuery`, иначе у кнопки остаётся индикатор ожидания. Результат отправляется новым сообщением, а сообщение с кнопками остаётся, чтобы можно было нажать другой период.

Данные callback приходят от клиента и могут быть подделаны, поэтому допустимые значения проверяются по белому списку `{7, 30, 90}` на сервере, а не берутся из строки как есть. Это же обеспечивает верхнюю границу 90 дней.

Существующий middleware для личных чатов работает и для `callback_query`: чат определяется по сообщению с кнопками.

### 9. Подписки

Чтение подписок и сопоставление через `store.listSubscriptions(chatId)` и `matchesKeyword`, как в `/schedule`. Отличие одно: без подписок команда не показывает кнопки и ничего не ищет, а выводит подсказку (в `/schedule` без подписок показывается всё).

### 10. Формат записей и разбиение на сообщения

- Строка: `дд.мм` (по `Europe/Kyiv`, через `Intl.DateTimeFormat`), значок статуса (только для записей не старше 3 дней), заголовок как ссылка на новость. Заголовок экранируется существующей `escapeHtml`. Год не нужен: период не превышает 90 дней, и дата однозначна.
- Порядок от новых к старым.
- Порог «свежести» в 3 дня сейчас локальная константа `/schedule`; её нужно вынести в общее место, чтобы два места не разошлись.
- Разбиение: записи накапливаются в сообщение, пока длина по сырому тексту (с HTML-тегами, то есть с запасом) не достигает 4000 символов, затем начинается следующее. Запись не режется. Заголовок с количеством идёт в начале первого сообщения.

### 11. Тексты

В `src/i18n.ts` добавляются ключи для приглашения выбрать период, подписей кнопок, подсказки без подписок, пустого результата и заголовка истории, на украинском и русском. Ошибка получения данных использует существующий текст `loadError`. Подписи «7 днів», «30 днів», «90 днів» во всех трёх случаях получаются с одним и тем же окончанием, поэтому склонение не нужно. Список команд в тексте `/start` дополняется `/history`.

### 12. Проверка

`scripts/check.ts` ходит на живой сайт, поэтому проверяются инварианты, а не конкретные записи: все результаты `fetchOutagesSince(90)` лежат в окне, окно 7 дней входит в окно 30, а оно в 90; чистые функции форматирования и разбиения проверяются на синтетических данных (запись не режется, ничего не теряется, лимит соблюдается, значки только у свежих записей). Диалог с кнопками проверяется вручную в Telegram.

## Risks / Trade-offs

- [Сайт недоступен или медленный] → ответ об ошибке (требование спецификации), кэш не хранит неудачные запросы.
- [Размер ответа с телами постов] → кэш на 5 минут и общий запрос на все периоды; при росте объёма перейти на двухшаговую загрузку (решение 6).
- [Предел страниц достигнут] → предупреждение в логе, пользователь получает уже загруженное. На текущем объёме (около 60 постов за 90 дней) до предела далеко.
- [Широкая подписка вроде трёхбуквенного корня даёт много записей] → разбиение на несколько сообщений (решение 10); отдельного лимита числа записей нет.
- [Фильтр отключений по заголовку не видит постов вроде «До уваги мешканців правосторонньої частини міста!»] → известное ограничение, общее с `/schedule`; в эту работу не входит.
- [Устаревший статус у старых постов] → значок скрыт у записей старше 3 дней (решение 10).
- [Подделанные данные нажатия кнопки] → белый список периодов (решение 8).

## Migration Plan

Миграции нет: схема базы и зависимости не меняются. Откат сводится к удалению команды и связанного кода; данные пользователей затронуты не будут.

Для варианта B в будущем: планировщик должен будет сохранять заголовок, дату и тело каждого отключения в новую таблицу, а `fetchOutagesSince` читать оттуда. Команду и тексты менять не придётся.
